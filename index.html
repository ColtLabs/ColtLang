Frequently Asked Questions

Everything about ColtaneDB

What is ColtaneDB and the Colt language?

ColtaneDB is an open-source, web-first data platform built around Colt, a custom query language. The product is a language, compiler, control plane, and query router over existing databases (Neon, Redis, Mongo, Firestore), rather than a proprietary storage engine.

Do I need to install a CLI or IDE to use it?

No installation is required. Colt Studio is the Official Web-Only IDE for Colt. You can write, parse, plan, import, and export .colt files directly from this web console. Python developers can also use our official coltanedb package on PyPI.

How are credentials and multi-tenant data protected?

TenantGuard isolates every tenant into their own schema (e.g., ct_tnt_...) or path namespace. Credentials live exclusively in server-side encrypted stores or environment variables, and are never logged or exposed in client bundles.

1. Platform Overview
          

          

            ColtaneDB provides a unified control plane and declarative language (Colt / .colt) over
            existing database providers. Rather than hosting a proprietary storage engine, ColtaneDB lexes, parses,
            validates, and emits parameterized execution plans targeted at PostgreSQL (Neon, Supabase), Redis (Upstash),
            Document stores (Firestore, MongoDB), and Edge SQLite (Turso).
          

        


        

          
2. Colt Query Grammar
          

          

            Colt syntax enforces strict typing, declarative backend placement via annotations
            (@backend(neon)), and clear primary key specifications (@key,
            @unique).
          

          
DEFINE COLLECTION users STRICT @backend(neon) {
  id: uuid @key,
  email: text @unique,
  tier: text @default("free")
}

FIND users SELECT email, tier WHERE tier == "pro"

        


        

          
3. TenantGuard
            Architecture

          

            Every tenant is designated an opaque ID (tnt_...). On PostgreSQL backends, TenantGuard creates
            dedicated physical schemas (ct_) and runs every query under SET LOCAL ROLE to
            guarantee that cross-tenant data leaks are physically blocked at the database kernel level.
